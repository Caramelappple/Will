# 과제 — 다음 프로젝트 준비 (2D · UI is Player)

이시온(LSO). Will 을 마치고 다음 프로젝트에 **그대로 가져갈 것**을 만든다.

## 주제가 정한 것

**UI 요소가 플레이어다.** 버튼·커서·체력바 같은 것이 직접 움직이는 주인공이다.
이 한 줄이 기술 선택을 거의 다 정해버린다.

```
플레이어의 자리는 Transform.position 이 아니라 RectTransform.anchoredPosition 이다
발판·적·벽은 Collider2D 가 아니라 Image 다
"화면 해상도" 가 연출이 아니라 게임 규칙이다
"누가 위에 그려지나" 가 보기 좋음이 아니라 게임 규칙이다
```

평소 2D 플랫포머 강의가 알려주는 것 —`Rigidbody2D`, `Physics2D`, `OnCollisionEnter2D` —
이 **거의 다 안 맞는다.** 유니티가 UI 에는 물리를 안 붙여주기 때문이다.
그래서 남이 대신 해주던 것을 직접 쓰게 되는데, 그게 이 과제의 이득이다.

## 이 과제의 목표

연습용으로 쓰고 버리지 않는다. 네 주가 끝나면 이런 상태여야 한다.

```
새 2D 프로젝트를 만들고
  → 폴더 하나를 복사해 넣으면
  → 움직이는 UI 플레이어 + 겹침 판정 + 창 쌓기가 바로 돈다
```

그래서 과제마다 **"다음 프로젝트에 복사해도 되는가"** 기준을 둔다.
특정 씬 이름·특정 오브젝트 이름·특정 해상도에 묶이면 복사할 수 없다.

## 규칙

1. 새 2D 프로젝트를 하나 만들고 거기서 한다. Will 을 건드리지 않는다
2. 과제를 **시작하기 전에** Will 의 비슷한 코드를 열지 않는다. 다 쓴 뒤에만 연다
3. 스크립트 이름에 `LSO_` 는 안 붙여도 된다. 그건 팀 규칙이지 개인 규칙이 아니다
4. **테스트는 인스펙터에서 해상도를 바꿔가며 한다.** 한 해상도에서만 되는 것은 안 된 것이다

## 0주차 — 먼저 정할 것 (1시간, 코드 없음)

이걸 안 정하고 시작하면 2주차에 전부 다시 쓴다. Will 에서 겪은 그 모양이다.

### 두 갈래가 있다

```
A안  Screen Space Canvas + 직접 계산
     플레이어가 anchoredPosition 으로 움직인다
     겹침 판정을 내가 쓴다 (2주차)

B안  World Space Canvas + Rigidbody2D

     겹침·중력·마찰을 유니티가 해준다
     대신 "UI" 의 이점(자동 배치·해상도 대응·EventSystem)을 거의 다 잃는다
```

### 정하고 한 문장으로 적을 것

프로젝트 루트에 `결정.md` 를 만들고 적는다.

```
우리는 (A안/B안) 을 쓴다. 왜냐하면 ____ 이다.
포기하는 것은 ____ 이다.
```

**포기하는 것을 못 적으면 아직 안 정한 것이다.** 둘 다 좋다고 적혀 있으면 틀렸다.

### 참고 — 주제에 맞는 쪽

`UI is Player` 라는 주제를 살리려면 **A안이다.** B안으로 가면
"UI 처럼 생긴 것이 나오는 평범한 2D 게임"이 되고, 주제가 연출로 내려앉는다.

그래도 스스로 답을 내볼 것. 아래 과제는 A안 기준으로 썼다.

### 손으로 먼저 확인할 것

```
Canvas 의 Render Mode 세 가지는 각각 무엇을 바꾸는가?
ScreenSpaceOverlay 캔버스 아래 오브젝트의 transform.position 을 찍으면 왜 수백이 나오는가?
anchoredPosition 이 (0,0) 인 것은 화면의 어디인가? — 답이 하나가 아니다. 왜인가?
```

세 번째가 핵심이다. 앵커와 피벗을 모르면 1주차 내내 자리가 어긋난다.

## 1주차 — RectTransform 을 움직이기 (2~3시간)

### 만들 것

좌우로 움직이고 점프하는 UI 플레이어. **딱 이것만.**

```
PlayerInputReader    입력을 읽어 값으로 들고 있는다
UiMover              anchoredPosition 을 옮긴다. 게임 규칙을 모른다
PlayerMotor          속도·중력·점프를 계산한다. RectTransform 을 모른다
```

**셋으로 나눈 이유가 이번 주의 절반이다.** `PlayerMotor` 는 순수 계산이라
UI 없이도 테스트할 수 있고, `UiMover` 는 "어디에 그리나"만 안다.

### 만족해야 할 것

- [ ] 좌우 이동이 **프레임 수와 무관하게** 같은 속도다
- [ ] **해상도를 1920×1080 에서 1280×720 으로 바꿔도 이동 속도가 같다**
- [ ] 점프 높이가 매번 같고, 해상도를 바꿔도 같다
- [ ] 화면 밖으로 나가지 않는다 — 경계를 `Screen.width` 로 구하지 않는다
- [ ] 자리를 정하는 곳이 **`UiMover` 하나다.** 다른 스크립트가 `anchoredPosition` 을 안 건드린다
- [ ] 플레이어 오브젝트에 `LayoutGroup` 이나 `ContentSizeFitter` 의 영향이 없다
- [ ] 이동 속도·점프 높이·중력이 전부 인스펙터 값이다
- [ ] 값의 단위가 주석에 적혀 있다 (px 인가, 기준해상도 단위인가)

### 하지 말 것

- `transform.position` 으로 이동 (`anchoredPosition` 을 쓴다)
- 경계 판정에 `Screen.width` / `Screen.height` 사용
  → 캔버스 루트의 `rect` 를 쓴다. Screen 은 캔버스 스케일을 모른다
- 부모에 `LayoutGroup` 을 두고 그 아래서 움직이기
- 매직 넘버. 숫자는 전부 `[SerializeField]`

### 이번 주의 진짜 함정

**`LayoutGroup` 과 자리싸움.** `HorizontalLayoutGroup` 아래에 플레이어를 두면
네가 `anchoredPosition` 을 써도 레이아웃이 매 프레임 되돌린다. 에러는 없다.
그냥 안 움직인다.

`CLAUDE.md` 의 *"자리·상태를 정하는 주체는 하나여야 한다"* 가 여기서 나온다.
Will 에서 겪은 촛불 회복 버그와 같은 종류다 — **두 곳이 같은 값을 쓴다.**

일부러 한 번 붙여보고 확인할 것. 그게 아래 실습 B다.

### 다 쓰고 스스로 답해보기

1. `Update` 에서 옮겼나, `FixedUpdate` 에서 옮겼나? UI 는 물리가 없는데 왜 그렇게 정했나?
2. 해상도를 바꿨을 때 속도가 같았나? 안 같았다면 무엇을 px 로 쓰고 있었나?
3. `CanvasScaler` 의 `Match Width Or Height` 를 0 과 1 로 바꾸면 게임이 어떻게 달라지나?
4. `PlayerMotor` 만 떼어내 `RectTransform` 없이 테스트할 수 있나? 못 하면 어디가 섞였나?

### 복사 가능성

- [ ] 이 셋을 다른 프로젝트에 넣고 빈 캔버스에 붙이면 **그대로 움직인다**
- [ ] 캔버스의 기준해상도가 달라도 돈다
- [ ] 씬에 특정 이름의 오브젝트가 없어도 터지지 않는다

## 2주차 — UI 끼리 부딪히게 하기 (3~4시간)

이번 주가 가장 어렵고, 가장 남는다. 유니티가 안 해주는 것을 직접 쓴다.

### 만들 것

```
UiBounds          RectTransform 을 공통 좌표계의 사각형으로 바꿔준다
UiOverlap         사각형 둘이 겹치는지, 어느 쪽에서 겹쳤는지 답한다
UiPlatform        밟히는 UI 하나. 밟혔다는 것을 자기는 모른다
UiCollisionProbe  플레이어가 발 밑·옆을 물어본다
```

### 만족해야 할 것

- [ ] 발판 위에 서면 멈춘다. 발판을 지나면 떨어진다
- [ ] 발판을 **아래에서 위로** 통과할 수 있다 (한 방향 발판)
- [ ] 벽에 붙어 밀어도 **끼거나 떨리지 않는다**
- [ ] 발판을 프리팹으로 열 개 복사해 놓으면 열 개 다 밟힌다
- [ ] 발판을 **런타임에 추가해도** 밟힌다 (목록을 `Awake` 에서 한 번만 모으지 않는다)
- [ ] 발판이 `LayoutGroup` 으로 배치되어 있어도 판정이 맞는다
- [ ] 해상도를 바꿔도 판정이 맞는다
- [ ] 겹침 계산이 **한 군데에만** 있다. 플레이어와 적이 같은 함수를 쓴다

### 알아야 하는 것

직접 찾아볼 것. 답을 여기 적어두지 않는다.

```
RectTransform.GetWorldCorners
Rect.Overlaps
RectTransformUtility.ScreenPointToLocalPointInRectangle
RectTransformUtility.RectangleContainsScreenPoint
```

넷 중 어느 것을 쓸지가 0주차에서 정한 좌표계에 달려 있다.
**섞어 쓰면 반드시 어긋난다.** 하나를 정하고 주석에 적을 것.

### 이번 주의 진짜 과제

**좌표계를 하나로 정하는 것.** 화면 좌표, 캔버스 로컬 좌표, 월드 좌표 셋이 돌아다니고
셋 다 `Vector2` 다. 타입이 같아서 컴파일러가 안 잡아준다.

```
각 함수가 무엇을 받아 무엇을 돌려주는지 표로 그려둘 것.
UiBounds 가 돌려주는 것이 무슨 좌표인지 클래스 주석 첫 줄에 적을 것.
```

Will 에서 까마귀 포식 마크가 90 유닛 밖으로 날아간 것이 이 문제였다 —
부모 스케일을 모르는 로컬 값을 그대로 썼다.

### 다 쓰고 스스로 답해보기

1. `UiBounds` 가 돌려주는 사각형은 무슨 좌표계인가? 왜 그걸 골랐나?
2. 한 방향 발판을 어떻게 판정했나? 속도 부호인가, 이전 프레임 자리인가?
3. 벽 끼임이 났다면 원인이 무엇이었나? 겹친 만큼 밀어냈나, 이동 전에 막았나?
4. 발판이 백 개면 매 프레임 몇 번 비교하나? 줄일 방법이 떠오르나? (아직 안 해도 된다)

### 복사 가능성

- [ ] `UiOverlap` 이 플레이어를 모른다. 어떤 UI 둘에도 쓸 수 있다
- [ ] `UiPlatform` 을 그대로 복사해 "적"이나 "아이템"으로 쓸 수 있다

## 3주차 — 상태로 정리하기 (2~3시간)

1·2주차 코드에 점프·낙하·대시·피격이 붙으면 `if` 가 엉킨다. 그 전에 정리한다.

### 만들 것

```
IPlayerState      Enter / Tick / Exit
StateMachine      상태 하나를 들고, 바꿔 끼운다
IdleState · RunState · JumpState · FallState
PlayerLook        상태가 정한 외형을 UI 에 바른다
```

### 만족해야 할 것

- [ ] `StateMachine` 은 **어떤 상태가 있는지 모른다.** `if (state is JumpState)` 가 없다
- [ ] 상태를 하나 더 추가할 때 `StateMachine` 을 고치지 않는다
- [ ] 상태가 바뀔 때 **Exit → Enter 순서**가 보장된다
- [ ] 같은 상태로 다시 들어가려 하면 어떻게 되는지 정해져 있다 (막든 다시 들어가든, 정하고 주석에 적을 것)
- [ ] 지금 상태 이름이 인스펙터에 보인다 (진단용)

### UI is Player 라서 더 붙는 것

플레이어가 UI 라서, **상태가 외형을 정하는 방식이 평소와 다르다.**
`Animator` 대신 `Image.sprite`·`color`·`RectTransform.sizeDelta` 를 바꾸게 된다.
그래서 "여기저기서 색을 바꾸는" 사고가 나기 쉽다.

- [ ] 색·스프라이트·크기를 바꾸는 곳이 **`PlayerLook` 하나다**
- [ ] 상태는 `PlayerLook` 에 "지금 이 상태다"만 알린다. `Image` 를 직접 안 만진다
- [ ] `sizeDelta` 를 상태가 바꾼다면, 2주차 겹침 판정이 **자동으로 따라간다**
      (크기를 두 곳에 적어두지 않았다는 뜻이다)

마지막 항목이 이번 주의 시험이다. 웅크리기를 추가해보면 바로 드러난다.

### 다 쓰고 스스로 답해보기

1. 상태 전환을 누가 결정하나? 상태 자신인가, 기계인가? 각각의 장단은?
2. `Exit` 에서 반드시 되돌려야 할 것은 무엇인가? 안 되돌리면 어떤 버그가 생기나?
3. 상태가 코루틴을 돌렸다면 `Exit` 에서 어떻게 멈추나?
4. 대시를 추가한다면 손대야 할 파일은 몇 개인가? 하나면 성공이다

### 비교

다 쓴 뒤 `Will/Assets/_Scripts/LSO/Tutorial/Gate/LSO_TutorialGateSO.cs`.

`Arm`/`Disarm` 과 `Enter`/`Exit` 가 같은 문제를 푼다. **짝이 맞아야 한다**는 것이 핵심이다.

## 4주차 — 창과 플레이어가 같은 캔버스에 있을 때 (3~4시간)

**이 주제에서만 생기는 문제다.** 평범한 게임은 UI 와 게임이 다른 층에 있어서
서로 모른 척할 수 있다. 여기서는 같은 캔버스에 있다.

### 만들 것

```
UIPanel           열고 닫히는 창 하나 (추상)
UIStack           창을 쌓고 되돌린다
InputLock         창이 떠 있는 동안 플레이어 조작을 막는다
PlayerRaycast     플레이어가 버튼을 누르는지 안 누르는지 정한다
```

### 만족해야 할 것

- [ ] `ESC` 로 일시정지 → 옵션 → `ESC` → 일시정지 → `ESC` → 게임. **순서대로 되돌아간다**
- [ ] 창이 하나라도 떠 있으면 플레이어가 안 움직인다
- [ ] 창이 **전부** 닫히면 조작이 돌아온다. 하나라도 남아 있으면 안 돌아온다
- [ ] 창을 두 개 겹쳐 열었다가 **한꺼번에 닫아도** 조작이 정확히 한 번 풀린다
- [ ] `Time.timeScale = 0` 이어도 UI 연출이 돈다
- [ ] **창이 플레이어보다 위에 그려진다.** 플레이어가 메뉴 위를 걸어다니지 않는다
- [ ] **플레이어가 UI 버튼 위를 지나가도 버튼이 안 눌린다** (또는 눌린다 — 정하고 적을 것)
- [ ] 마우스로 버튼을 누를 때 플레이어가 막지 않는다

### 이번 주의 진짜 과제 — 둘이다

**첫째, 잠금을 세는 것.** `bool` 하나로 만들면 반드시 깨진다.
창 둘을 열고 하나만 닫았는데 조작이 풀리는 것 — 세어야 한다.
Will 의 `LSO_HoverMoveEffect` 가 `_suspendCount` 로 센 것과 같은 문제다.

**둘째, 그리는 순서가 게임 규칙이 된 것.** 평소 UI 의 `sibling index` 는
보기 좋음의 문제지만, 여기서는 *"플레이어가 벽 뒤에 있나 앞에 있나"* 다.

```
누가 sibling index 를 정하나?
창을 열 때 SetAsLastSibling 을 부르는 곳이 몇 군데인가?
플레이어의 자리를 계층에서 고정할 수 있나? 그러면 창은 어디에 두나?
```

**정하는 주체가 하나여야 한다.** `UIStack` 이 정하게 하는 것이 자연스럽다.

### 알아야 하는 것

```
Graphic.raycastTarget
CanvasGroup.blocksRaycasts / interactable
EventSystem.current.IsPointerOverGameObject()
Canvas.overrideSorting / sortingOrder
Transform.SetAsLastSibling
```

### 다 쓰고 스스로 답해보기

1. 잠금을 세는 것과 "열린 창 목록의 개수를 보는 것" 중 어느 쪽이 나은가? 왜?
2. 창이 파괴되면서 닫히지 못하면? 잠금이 영영 남는 것을 어떻게 막았나?
3. `timeScale = 0` 에서 안 도는 것은 무엇인가? 어떻게 우회했나?
4. `ESC` 를 창과 플레이어가 둘 다 듣고 있으면? (Will 에서 실제로 겪은 것이다)
5. 플레이어가 버튼을 누르게 하려면 `EventSystem` 을 어떻게 쓰나?
   안 누르게 하려면? 둘 중 어느 쪽이 기본값이어야 하나?

### 복사 가능성

- [ ] 새 창을 만들 때 `UIPanel` 을 상속하고 프리팹만 만들면 끝난다
- [ ] `UIStack` 을 고치지 않는다

## 실습 셋 — 각 1시간, 순서 상관없음

읽지 말고 **직접 깨볼 것.**

### A — 해상도가 게임 규칙일 때

```
1. 1주차 플레이어를 띄운다
2. Game 창에서 1920×1080 → 1280×720 → 800×600 → 2560×1080 로 바꿔본다
3. 같은 시간 동안 달린 거리를 비교한다
4. CanvasScaler 를 Constant Pixel Size 로 바꿔보고 같은 것을 한다
5. Match Width Or Height 를 0 / 0.5 / 1 로 바꿔본다
```

**어떤 조합에서 게임이 불가능해지는가.** 세로로 긴 화면에서 점프가 발판에 안 닿는 것을
보면 *"해상도 대응은 나중에"* 가 왜 틀린 말인지 끝난다.

### B — 자리를 두 곳이 정하면

```
1. 1주차 플레이어의 부모에 HorizontalLayoutGroup 을 붙인다
2. 움직여본다
3. anchoredPosition 을 Debug.Log 로 찍어본다 — 값은 바뀌는가?
4. ContentSizeFitter 로 같은 것을 해본다
5. LayoutGroup 을 지우지 않고 움직이게 만들 방법을 찾아본다
```

3번이 중요하다. **값은 바뀌는데 화면은 안 바뀐다.** 에러도 없다.
Will 에서 촛불이 매 스테이지 회복된 것과 같은 모양이다 — 코드 검색으로 안 잡히는 결합.

### C — 같은 클릭을 두 곳이 읽으면

```
1. 플레이어와 버튼을 겹쳐놓는다
2. 플레이어를 클릭한다 — 버튼이 눌리는가?
3. 플레이어의 Image 에서 Raycast Target 을 끄고 다시 해본다
4. 컴포넌트 둘이 같은 프레임에 ESC 를 읽게 만든다. A 는 일시정지, B 는 창 닫기
5. ESC 를 한 번 누른다
```

Will 에서 소환한 기물이 자동 선택 안 된 것과 같다 — 한 프레임의 클릭을 둘이 먹었다.
**키를 나누는 법**과 **먼저 받은 쪽이 소비하는 법** 둘 다 해볼 것.

### D — 구독을 안 풀면

```
1. 정적 이벤트를 가진 매니저를 만든다
2. 구독만 하고 해제 안 하는 UI 를 만든다
3. 그 UI 오브젝트를 껐다 켠다. 세 번쯤
4. 이벤트를 한 번 쏜다
```

**몇 번 반응하는가.** 3주차 `Exit`, 4주차 `OnDisable` 이 왜 필요한지 여기서 끝난다.
